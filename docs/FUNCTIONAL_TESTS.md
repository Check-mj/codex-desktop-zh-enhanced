## 回归测试政策（T9–T12 保留）

以下故障注入测试属于发布前必查项，**不因版本迭代删除**：

- **T9** 签名失败阻止部署（`sign.ps1` / `重新构建.ps1` / `打包安装版.ps1`）；
- **T10** 重建前置步骤失败不破坏旧版本（下载/哈希/构建/签名四类注入）；
- **T11** 部署后半段失败时 exe 与源码双回滚；
- **T12** 源码树哈希回滚校验（含篡改检测）。

规则：

1. 每次发布前核对 T9–T12 记录仍有效（对应脚本未变化时可直接引用；脚本变化则重跑）；
2. 未来出现真实用户问题时，**先补充一条对应测试**（记录故障场景与复现方法），再修复；
3. 未实际执行的测试不写“通过”，只写“未测试”或“未覆盖”。

## 详细记录

### T1 正常启动

- 启动 `Codex-Zh-Launcher-Windows-x64.exe`，约 7 秒后出现带窗口的 UI 进程。
- 关闭 UI 后，监督 / 守护进程仍为 2 个，后台功能不受影响。

### T2 守护自恢复

- 找到 `--guard` 进程并强杀（模拟崩溃）。
- 8 秒内出现新的 `--guard` 进程（PID 15024）。
- 日志：`2026-10-19 00:30:12.222  supervisor.restart code=-1`。

### T3 长会话保护

- 停止启动器，关闭 Codex，用系统入口裸启动 Codex（英文），等待 35 秒。
- 启动守护，等待 12 秒。
- 日志：`2026-10-19 00:31:09.473  guard.skip-long-running count=9`。
- Codex 进程数保持 9，未被强杀。

### T4 异常退出恢复

- 守护运行、Codex 已确认中文（`locale=True`）的情况下，强杀全部 Codex 进程。
- 12 秒后 Codex 进程数为 0，没有被守护重新拉起。
- 日志：`guard.codex-exited`。
- 之后手动 `--launch-zh` 恢复正常（`locale=True`）。


### T7 开机自启链路（模拟登录）

由于无法真实重启本机，按如下方式模拟 Windows 登录时执行自启项：

1. 记录注册表中的自启命令：
   `"D:\Codex汉化\Codex-Zh-Launcher-Windows-x64.exe" --supervise`
2. 结束全部启动器与 Codex 进程（模拟关机后的进程状态；`%LOCALAPPDATA%\CodexZhLauncher` 下的状态文件保留，
   与真实重启一致）。
3. 以该命令启动（等价于 Explorer 执行 Run 项）。

实测时间线：

> 说明：这是**模拟**登录链路，验证了自启命令、进程拉起、注入、状态写入的完整性；

### 本次回归发现并修复的问题

**问题**：v0.8.1 首次构建的安装包中，`卸载.ps1` / `uninstall.ps1` 缺少 UTF-8 BOM；
在 Windows PowerShell 5.1 下按 ANSI 解析会导致中文乱码、脚本报错（卸载失败）。

**修复**：

- 所有脚本统一加 UTF-8 BOM；
- 重新构建安装包；
- 从 zip 的 `payload` 中提取 `卸载.ps1` / `uninstall.ps1` 验证：BOM 存在、语法解析通过。

> 该问题只影响安装包内的脚本副本，不影响已部署的主程序；安装包已重新生成并替换发布资产。

3. 验证：

### T9 签名失败必须阻止部署（故障注入测试）

- 用错误指纹调用 `sign.ps1`：抛出异常，退出码 **1**。
- 临时把 `sign.ps1` 替换为必然失败的脚本后运行 `重新构建.ps1`：
  在签名步骤中止，退出码 **1**，主程序 exe 哈希**前后一致**（未被替换）。
- 同样替换后运行 `打包安装版.ps1`：中止打包，退出码 **1**。
- 恢复真实 `sign.ps1` 后重新签名/打包：状态 `Valid`，流程正常。
### T10 重建失败不破坏现有源码与主程序（故障注入）

测试方法：记录「源码目录树哈希」与「主程序 SHA-256」，然后分别制造故障并运行
`重新构建.ps1 -Update -NoPause`，检查退出码与两者是否变化。

| 故障 | 退出码 | 源码未变 | exe 未变 |
|---|---|---|---|
| 上游仓库地址无效（下载失败） | 1 ✅ | ✅ | ✅ |
| 源码包 SHA-256 不匹配 | 1 ✅ | ✅ | ✅ |
| overlay 引入无法编译的文件（构建失败） | 1 ✅ | ✅ | ✅ |
| 签名脚本强制失败 | 1 ✅ | ✅ | ✅ |
| 正常流程 | 0 ✅ | 已更新 | 已更新（签名 Valid） |

结论：任何前置步骤失败都不会删除或覆盖现有源码与旧 exe；只有全部验证通过才部署。
### T11 部署后半段失败：EXE 与源码一起回滚

场景：主程序已经原子替换完成，随后源码目录交换失败。要求旧 exe 与旧源码都被恢复。

测试方法：记录 exe SHA-256 与源码树哈希，用注入故障的脚本副本运行 `-Update`，在源码交换阶段抛错：

| 失败点 | 结果 |
|---|---|
| 源码交换开始前（尚未移动任何目录） | 退出码 1；提示“已完整回滚”；exe 哈希恢复 ✅；源码树恢复 ✅ |
| 旧源码已移走、新源码未就位 | 退出码 1；提示“已完整回滚”；exe 哈希恢复 ✅；源码树恢复 ✅ |

同时确认：

- 程序目录无 `*.new` / `*.restore` 残留；
- 旧 exe 由同卷 `File.Replace` 原子移入 `backups\pre-update-*`，回滚时同样原子恢复；
- 若自动回滚失败，错误信息会明确给出备份路径并提示手动恢复（不假装成功）。

> 注：首版回滚代码使用了不存在的 `File.Replace` 两参数重载，导致回滚失败；
> 本次测试发现并修复为三参数原子替换，上述结果均为修复后的复测结果。
### T12 源码回滚的完整树哈希校验

T11 中的“源码恢复”最初只检查 `build.ps1` 是否存在，不能证明整棵树完整。现改为：

1. 交换源码前记录旧源码树哈希：`相对路径 + 文件大小 + 文件 SHA-256` 的汇总 SHA-256；
2. 回滚恢复后重新计算并比较；
3. 只有 **exe 哈希与源码树哈希都一致** 才输出“已完整回滚”，否则输出“自动回滚未完全成功”并给出备份路径。

故障注入结果：

| 用例 | 结果 |
|---|---|
| A：源码交换开始前失败 | 退出码 1；提示“已完整回滚（源码树哈希 …）”；exe 与源码树哈希均恢复 ✅ |
| B：旧源码已移走、新源码未就位 | 同上 ✅ |
| C：回滚后故意篡改一个文件 | 退出码 1；**拒绝**输出“已完整回滚”，提示“自动回滚未完全成功”；exe 仍恢复 ✅ |

用例 C 证明：树哈希校验能识别“看似恢复、实际不完整”的情况，而不是永远报告成功。
